# MathLLM 开发指南

## 一、这个项目在做什么

### 一句话概括

把一个通用的 7B 小模型，通过 LoRA 精调训练，变成一个**专门擅长解数学题**的模型，然后把它部署成一个可以交互的 Web 应用。

### 完整链路

```
[数学题目数据] → [数据清洗/格式化] → [LoRA 精调 Qwen2.5-7B] → [合并权重] → [INT4 量化] → [vLLM 部署] → [FastAPI + Gradio 应用]
                                                                                                              ↓
                                                                                                        [评测体系：准确率/延迟/幻觉率]
```

你在做的事情，本质上和大厂 AI 团队的工作一模一样：拿到一个基座模型，用自己的数据让它变强，然后做成产品。

### 项目亮点（面试时主动讲的）

**1. 全链路闭环**
不只是调 API 写个 Demo。你从数据准备到模型精调、量化部署、应用开发、评测体系全部自己做了一遍。这说明你理解 AI 应用的完整生命周期，不是只会写 Prompt 的调包侠。

**2. 小模型打败大模型（在特定领域）**
精调后的 7B 模型在数学解题任务上接近 GPT-4 的效果，但推理成本降低 95%。这是 AI 工程的核心价值——**用最少的资源达到最好的效果**。

**3. 有数据支撑**
你不是说"效果很好"，而是有消融实验、有对比评测、有准确率/延迟/幻觉率的具体数字。这是工程师思维和 Demo 思维的区别。

**4. 你的信计专业真正用上了**
LoRA 的低秩分解是线性代数，评测指标的设计需要统计学，消融实验需要实验设计方法论。你学的数学在这里不是摆设，是核心竞争力。

### 需要你仔细研究的地方

以下每个点你都要能**用自己的话讲清楚**，面试官会追问：

| 知识点 | 你需要理解到什么程度 | 怎么学 |
|--------|-------------------|--------|
| **LoRA 原理** | 能写出 W' = W + BA 的公式，解释为什么低秩就够了，rank 怎么选 | 看 LoRA 论文 + 本项目 design.md |
| **QLoRA vs LoRA** | 知道 4bit 量化加载基座模型 + LoRA adapter 训练的区别 | 看 HuggingFace PEFT 文档 |
| **vLLM PagedAttention** | 能说清楚它怎么解决 KV Cache 显存碎片化问题，类比操作系统虚拟内存 | 看 vLLM 论文 + 官方文档 |
| **INT4 量化原理** | AWQ 和 GPTQ 的区别，为什么 AWQ 对数学场景更好 | 看 AWQ 论文摘要 + 实验部分 |
| **ChatML 格式** | 理解 system/user/assistant 三角色对话格式，为什么精调要用这个格式 | 看 Qwen 官方文档 |
| **Loss 曲线** | 能看懂训练 loss 和 eval loss 的变化趋势，判断是否过拟合 | 训练时观察 + 搜"如何看 loss 曲线" |
| **消融实验方法论** | 知道为什么要做消融实验，控制变量法的意义，怎么判断哪个参数影响最大 | 看本项目 design.md 消融实验部分 |

> **学习方式建议**：不需要从头读论文。每个知识点先搜"XX 通俗解释"或"XX 图解"，理解了核心思想再看本项目 design.md 里的面试话术部分。目标不是成为研究者，而是**面试时能讲清楚原理和你的选择理由**。

## 二、开发顺序与技术要点

### 开发顺序（四周计划）

```
Week 1: 数据（最重要，决定上限）
  ├── 收集数据
  ├── 写 prepare_data.py
  └── 检查数据质量

Week 2: 训练 + 部署
  ├── LoRA 精调
  ├── 合并权重
  ├── 量化
  └── vLLM 部署

Week 3: 应用开发
  ├── FastAPI 后端
  ├── Gradio 前端
  └── 端到端测试

Week 4: 评测 + 打磨
  ├── 评测体系
  ├── 消融实验
  ├── Docker 部署
  └── 整理文档
```

### 每个阶段的详细开发要点

#### Week 1：数据准备（最关键）

**核心认知：数据质量决定模型上限，训练技巧只能逼近这个上限。**

| 任务 | 具体做法 | 注意 |
|------|---------|------|
| 收集数据 | 从 HuggingFace 下载 GSM8K/MATH，整理考研真题，用 GPT-4 生成补充数据 | 优先保证质量，宁少勿多 |
| 格式转换 | 实现 `prepare_data.py`，转为 ChatML 格式 | system prompt 要精心设计，影响模型行为 |
| 数据清洗 | 去重、去空、去太短/太长的样本 | 每条数据人工抽查 10% 看质量 |
| 划分数据集 | 90% train / 10% eval，随机打乱 | eval 集要确保和 train 没有重叠 |

**技术要点：**
- 数据格式必须和 Qwen2.5 的 chat template 完全一致，否则训练会崩
- solution 字段要包含完整解题步骤，不能只有答案
- 数学公式用 LaTeX 格式（`$...$`），训练数据里的格式就是模型输出的格式

#### Week 2：训练与部署

| 任务 | 具体做法 | 注意 |
|------|---------|------|
| LoRA 精调 | 推荐用 LLaMA-Factory CLI，一行命令启动 | 先小数据（100条）跑通流程，再上全量 |
| 观察 Loss | 训练时监控 loss 曲线 | train loss 下降 + eval loss 上升 = 过拟合，需要早停 |
| 合并权重 | `merge_lora.py` 合并 adapter 到基座 | 合并后模型体积 = 基座体积，约 14GB |
| 量化 | INT4 量化，约 4GB | 量化后必须测试一下效果是否有明显下降 |
| vLLM 部署 | `server.py` 启动服务 | 先用 FP16 跑通，再换 INT4 看速度提升 |

**技术要点：**
- **先小后大**：用 100 条数据 + 1 epoch 先跑通整个训练流程，确认没有 bug，再上全量
- **rank 选择**：先用默认 r=16 训练一次，消融实验放 Week 4
- **显存不够怎么办**：减小 batch_size 到 1，增大 gradient_accumulation_steps 到 16
- **LLaMA-Factory vs 自写训练脚本**：新手推荐 LLaMA-Factory，配置简单稳定；自写脚本用于理解原理

#### Week 3：应用开发

| 任务 | 具体做法 | 注意 |
|------|---------|------|
| FastAPI 后端 | 实现 /api/solve 和 /api/chat 接口 | 核心是调用 vLLM 的 OpenAI 兼容 API |
| 流式输出 | 用 SSE（Server-Sent Events）实现逐字输出 | 用 sse-starlette 库，不要用 WebSocket（过度设计） |
| Gradio 前端 | 用 gr.Chatbot 组件，支持 LaTeX 渲染 | Gradio 内置 Markdown/LaTeX 渲染，不需要额外配置 |
| 端到端测试 | 手动测试 20-30 道题 | 记录 Bad Case，分析是模型问题还是应用层问题 |

**技术要点：**
- FastAPI 调用 vLLM 用 **httpx**（异步 HTTP 客户端），不要用 requests（会阻塞流式输出）
- 多轮对话要正确拼接历史消息，system prompt 只放第一条
- Gradio 的 Chatbot 组件原生支持 Markdown + LaTeX，直接用即可

#### Week 4：评测与打磨

| 任务 | 具体做法 | 注意 |
|------|---------|------|
| 多维度评测 | 实现 `evaluate.py` 的全部评测维度 | 准确率最重要，先做好这个 |
| 对比实验 | 精调模型 vs 基座模型 vs GPT-4 | 用同一份 eval 集测试，保证公平 |
| 消融实验 | 跑 3-4 组不同 rank 的训练 | 每组只需训练 1 epoch 就够了（节省时间） |
| 生成图表 | 用 matplotlib 画对比柱状图和折线图 | 图表要写进 README，视觉冲击力强 |
| Docker 部署 | 写 Dockerfile，一键启动 | 先本地跑通，再考虑上云 |

**技术要点：**
- **答案判分**：数学答案提取是关键难点。数值答案用正则提取 + 容差比较；表达式答案可以用 sympy 化简后比较
- **LLM-as-Judge**：用 GPT-4 给解题过程打分，Prompt 要给明确的评分标准（rubric），否则分数不稳定
- **消融实验不需要跑满**：每个配置只需 1 epoch + 小数据集（200条）就能看出趋势

## 三、AI 开发 vs 你需要自己理解的部分

### 分类原则

- **可以用 AI 写的**：模式固定的代码、格式转换、胶水逻辑、UI 搭建、配置文件
- **需要你理解的**：涉及决策选择的、需要判断对错的、面试会被追问的

### 详细分类

#### 完全可以用 AI 开发的部分

这些部分你只需要告诉 AI "帮我实现 XX 功能"，AI 写出来的代码基本可以直接用：

| 模块 | 文件 | 为什么 AI 能写 |
|------|------|---------------|
| 数据格式转换 | `prepare_data.py` | 输入输出格式明确，是纯数据管道逻辑 |
| FastAPI 接口 | `app/api/main.py` | 标准 CRUD 模式，AI 写过几百万次了 |
| Gradio 界面 | `app/frontend/gradio_app.py` | 声明式 UI，AI 最擅长写这种模板代码 |
| Docker 配置 | `deploy/Dockerfile` | 配置固定，AI 完全能写 |
| 图表生成 | `eval/evaluate.py` 的画图部分 | matplotlib 画图是 AI 的强项 |
| 正则提取答案 | `eval/evaluate.py` 的判分部分 | 正则表达式是 AI 最擅长的 |
| HTTP 调用封装 | 调用 vLLM API 的代码 | 标准的 httpx 异步调用 |
| 数据校验 | `validate_data()` 函数 | 过滤逻辑，规则明确 |

**怎么用 AI：** 直接把文件骨架丢给 Cursor/Copilot，说"请实现所有 TODO 部分"，然后逐文件检查。

#### 需要你理解后选择，再用 AI 辅助实现的部分

这些部分你必须**先做决策**，然后让 AI 帮你写代码：

| 模块 | 你需要做的决策 | 为什么不能全靠 AI |
|------|-------------|----------------|
| **System Prompt 设计** | 定义模型的行为规范、输出格式、语气风格 | Prompt 设计是产品决策，AI 不知道你想要什么样的解题风格 |
| **数据筛选策略** | 哪些数据要保留，哪些要丢弃，阈值怎么定 | 需要你对数学题质量的判断，信计背景在这里发挥作用 |
| **LoRA 超参数选择** | rank、alpha、target_modules 的具体值 | 面试必问，你必须知道为什么选这个值 |
| **训练配置** | 学习率、epoch、batch_size 的设定和调整 | 需要根据 loss 曲线动态调整，不能一键跑完不管 |
| **量化方案选择** | AWQ vs GPTQ vs bitsandbytes，选哪个为什么 | 面试会问，你需要理解区别 |
| **评测指标设计** | 准确率怎么算、过程分怎么评、幻觉怎么检测 | 评测方法论是你工程能力的体现 |
| **消融实验设计** | 对比哪些变量、怎么控制变量、怎么分析结果 | 实验设计能力是加分项 |
| **错误分析** | 模型答错的题是为什么，怎么改进 | 需要你懂数学才能分析模型错在哪 |

**怎么用 AI：** 先自己想清楚方案，然后让 AI 帮你实现。例如：

> "我决定用 LoRA rank=16, alpha=32, 作用在 q/k/v/o/gate/up/down 投影层上。请帮我写 train_config.yaml 的 lora 配置部分。"

#### 必须你自己做的事情（AI 帮不了）

| 事情 | 为什么 |
|------|--------|
| **跑训练并观察 Loss** | 你需要看到 loss 曲线，判断是否过拟合，决定是否调整参数 |
| **检查模型输出质量** | 模型解出来的题你得自己验算，判断是真好还是幻觉 |
| **调试部署问题** | GPU 显存不够、推理报错、API 超时——这些需要你亲自排查 |
| **准备面试话术** | 你必须用自己的语言讲清楚每个技术决策，AI 帮不了你面试 |
| **写简历描述** | 你需要用数据总结项目成果，这是你的个人经历 |

### 推荐的 AI 辅助开发流程

```
第一步：你阅读对应模块的设计文档（docs/design.md 对应章节）
         ↓
第二步：你做技术决策（选框架/选参数/定方案）
         ↓
第三步：你把决策 + 文件骨架丢给 AI，让它填充实现
         ↓
第四步：你 review AI 写的代码，重点检查：
         - 输入输出是否符合预期
         - 有没有明显的逻辑错误
         - 异常处理是否完善
         ↓
第五步：跑起来测试，发现 bug 再让 AI 修
```

### 按开发顺序的 AI 使用建议

| 阶段 | AI 参与度 | 你的角色 |
|------|----------|---------|
| Week 1 数据准备 | 70% AI | 你负责筛选数据、设计 system prompt、检查数据质量 |
| Week 2 训练部署 | 50% AI | 你负责选超参数、观察 loss、判断过拟合、选量化方案 |
| Week 3 应用开发 | 90% AI | FastAPI + Gradio 几乎全部让 AI 写，你负责测试和调优 |
| Week 4 评测打磨 | 60% AI | 你负责设计评测维度、分析结果、做实验设计，AI 写代码和画图 |

### 5.3 各数据集格式说明

**GSM8K 格式：**
```json
{"question": "Janet's dogs eat 3 bags of food per day. How many bags do they eat in 2 weeks?", "answer": "3 * 14 = 42\n#### 42"}
```
- 需要把 `answer` 字段拆分为 `solution`（推理过程）和 `final_answer`（最终答案）
- GSM8K 的答案格式是 `推理过程\n#### 最终答案`，用 `\n#### ` 分割即可

**MATH 格式：**
```json
{"problem": "Find the value of $x$ such that $\\sqrt{x+5} = 3$", "solution": "Squaring both sides: $x+5 = 9$, so $x = 4$.", "level": "Level 1", "type": "Algebra"}
```
- 字段名不同：`problem` → `question`，`solution` 直接可用
- 有 `level` 和 `type` 字段，可以用来做难度筛选

### 5.4 数据混合策略

建议训练集混合比例：

| 数据来源 | 数量 | 占比 | 理由 |
|---------|------|------|------|
| GSM8K 训练集 | 500 条 | 40% | 基础计算能力 |
| MATH 训练集 | 500 条 | 40% | 高数/线代/概率论覆盖 |
| GPT-4 生成 | 200 条 | 15% | 补充你想要但数据集里没有的题型 |
| 考研/大学数学 | 100 条 | 5% | 覆盖信计专业课的题型 |

总计约 **1300 条**，足够 LoRA 精调出明显效果。

```python
prompt = """请生成 5 道大学高等数学题目，要求：
1. 涵盖求导、积分、极限、级数等不同类型
2. 每道题包含完整的解题过程
3. 解题步骤详细，适合教学生学习
4. 用 LaTeX 格式书写公式
5. 输出 JSON 格式：[{"question": "...", "solution": "...", "answer": "..."}]"""
```

注意：GPT-4 生成的数据**一定要人工检查**，尤其是数学推导是否正确。GPT-4 在复杂计算上会出错。

## 六、常见报错排查

### 6.1 训练阶段

| 报错 | 原因 | 解决方案 |
|------|------|---------|
| `CUDA out of memory` | 显存不够 | 减小 batch_size 到 1，增大 gradient_accumulation_steps；或用 QLoRA（4bit 加载） |
| `Loss 不下降或反复震荡` | 学习率太大 | 学习率从 2e-4 降到 1e-4，或从 5e-5 开始 |
| `Loss 降到 0 附近` | 数据量太少或数据重复 | 检查数据是否有重复，增加数据多样性 |
| `train loss 下降但 eval loss 上升` | 过拟合 | 减少 epoch 数、增加数据量、降低 rank |
| `模型输出全是乱码/重复文本` | 训练崩溃 | 检查数据格式是否正确、chat template 是否匹配 |
| `RuntimeError: shape mismatch` | 数据预处理 bug | 检查 tokenized 后的 input_ids shape |
| `OOM during evaluation` | eval 时 batch 太大 | 设置 `per_device_eval_batch_size=1` |

### 6.2 合并与量化阶段

| 报错 | 原因 | 解决方案 |
|------|------|---------|
| `ModuleNotFoundError: peft` | 没装 peft 库 | `pip install peft` |
| `合并后模型输出和训练时不一样` | 合并过程有误 | 确认使用了 `merge_and_unload()`，且保存格式正确 |
| `AWQ 量化报错` | autoawq 版本不兼容 | `pip install autoawq --upgrade` |
| `量化后准确率大幅下降` | 量化精度损失太大 | 换 INT8 量化，或用 AWQ 替换 GPTQ |

### 6.3 部署阶段

| 报错 | 原因 | 解决方案 |
|------|------|---------|
| `vLLM 启动报 CUDA OOM` | 模型太大，显存不够 | 使用 INT4 量化模型，或降低 `gpu_memory_utilization` |
| `vLLM 启动很慢` | 首次加载需要编译 CUDA kernel | 正常现象，首次启动需 1-3 分钟 |
| `API 返回 502/504` | vLLM 服务没启动或超时 | 检查 vLLM 是否正常运行，增加超时时间 |
| `流式输出不工作` | SSE 配置问题 | 检查 FastAPI 的 response type 是否正确设置了 `text/event-stream` |
| `多请求并发时延迟飙升` | 批处理能力不足 | 增加 vLLM 的 `max_num_seqs` 参数 |

### 6.4 应用层

| 报错 | 原因 | 解决方案 |
|------|------|---------|
| `Gradio LaTeX 公式不渲染` | 公式格式不对 | 行内公式用 `$...$`，块级公式用 `$$...$$`，不要用 `\(...\)` |
| `多轮对话丢失上下文` | 消息拼接逻辑有 bug | 检查 messages 列表是否正确包含了所有历史消息 |
| `中文乱码` | 编码问题 | 确保所有文件使用 UTF-8 编码，JSON 写入用 `ensure_ascii=False` |

### 6.5 排查思路（万能方法）

1. **先搜报错信息**：复制完整报错信息到 Google/Bing 搜索，90% 的问题都有人遇到过
2. **简化复现**：把问题缩到最小——用 10 条数据训练、用最小的模型测试
3. **对比官方文档**：检查你的配置和官方示例的差异
4. **问 AI**：把完整报错 + 你的配置丢给 ChatGPT/Claude，让它帮你分析

## 九、进阶扩展方向

基础版本做完后，如果还有时间，以下功能可以进一步提升含金量（按性价比排序）：

### 9.1 RAG 增强（推荐，1-2天可完成）

**做什么**：让模型在解题前，先检索相关的公式和定理作为上下文。

```
用户输入题目 → 检索相关公式/定理 → 拼接到 Prompt → 模型解题
```

**为什么值得做**：
- 简历上多了"RAG"关键词，覆盖面更广
- 可以对比"精调 alone" vs "精调 + RAG"的效果，多一组实验数据
- 实现简单：用 LangChain + FAISS/Chroma 搭一个向量检索即可

**面试加分点**：你能讲清楚"什么场景需要 RAG，什么场景精调就够了"。

### 9.2 自我验证 / Chain-of-Thought Verification（推荐，1天）

**做什么**：模型解题后，再让模型自己检查一遍答案是否正确。

```
解题 → 验证：把答案代回原题检验 → 如果错误则重新解答 → 输出最终答案
```

**为什么值得做**：
- 展示了你对 LLM 幻觉问题的思考
- 体现了 Agent 化的工程思维
- 实现简单，就是在 Prompt 里加一步验证指令

### 9.3 多模型对比界面（1天）

**做什么**：在 Gradio 界面上同时展示基座模型、精调模型、GPT-4 的回答，让用户直观对比。

**为什么值得做**：
- 面试演示效果极佳：三个模型同时答题，精调模型的表现一目了然
- 体现你对模型评测的深度理解

### 9.4 模型监控与告警（2-3天）

**做什么**：追踪每次推理的延迟、Token 消耗、错误率，做成 Dashboard。

**为什么值得做**：
- 展示了 MLOps 思维
- 面试大模型工程岗时可以讲"模型上线后怎么监控"
- 用 Prometheus + Grafana 实现，技术栈加分

### 9.5 难度自适应（进阶，2-3天）

**做什么**：根据题目难度自动选择不同的解题策略——简单题直接回答，难题用多步推理 + 自我验证。

**为什么值得做**：
- 展示了系统设计能力（路由策略）
- 体现了对推理效率的思考

### 扩展功能优先级

| 功能 | 耗时 | 简历加分 | 面试话题量 | 推荐优先级 |
|------|------|---------|-----------|-----------|
| RAG 增强 | 1-2天 | ⭐⭐⭐ | 多 | 🥇 |
| 自我验证 | 1天 | ⭐⭐ | 中 | 🥈 |
| 多模型对比 | 1天 | ⭐⭐ | 中 | 🥉 |
| 模型监控 | 2-3天 | ⭐⭐ | 多 | 4 |
| 难度自适应 | 2-3天 | ⭐⭐⭐ | 多 | 5（时间充裕再做） |

## 十、各模块时间预估

以下是每个模块的**预计耗时**，帮你合理安排时间：

| 模块 | 预计耗时 | 说明 |
|------|---------|------|
| 环境搭建 | 2-4h | 第一次配 GPU 环境会比较折腾 |
| 数据下载与探索 | 3-4h | 下载数据集、看数据格式、确定用哪些数据 |
| prepare_data.py | 3-5h | AI 写代码 1h + 你调试和检查 2-4h |
| 第一次训练（小数据跑通） | 2-3h | 100 条数据 1 epoch，验证流程无 bug |
| 全量训练 | 2-4h | 等待训练完成 + 观察 loss 曲线 |
| 合并权重 + 量化 | 1-2h | 脚本简单，跑一下就好 |
| vLLM 部署 | 2-3h | 启动服务 + 测试 API |
| FastAPI 后端 | 4-6h | AI 写代码 2h + 调试 2-4h |
| Gradio 前端 | 3-4h | AI 写代码 1h + 调试和美化 2-3h |
| 评测脚本 | 5-8h | 判分逻辑是难点，需要反复调试 |
| 消融实验 | 4-6h | 3-4 组实验，每组 1h 训练 + 0.5h 评测 |
| 生成图表 | 2-3h | 让 AI 写画图代码 |
| Docker 部署 | 2-3h | 写 Dockerfile + 测试 |
| 文档整理 | 3-4h | 更新 README + 补充架构图 |
| 演示视频录制 | 1-2h | 录制 + 剪辑 |
| **总计** | **约 40-60h** | 按每天 4-6h 有效开发，约 2-3 周 |

### 时间分配建议

- **前紧后松**：Week 1-2 多花时间，Week 3-4 留 buffer 给意外情况
- **训练时间利用**：训练时 GPU 在跑，你可以同时写应用层代码
- **不要追求完美**：第一版能用就行，后面再迭代优化
- **卡住超过 2 小时就换方向**：别在一个 bug 上死磕，先做其他模块，回头再解决
