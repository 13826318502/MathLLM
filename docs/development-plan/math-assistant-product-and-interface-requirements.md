# MathLLM 数学题目问答助手：功能与界面需求报告

> 本报告用于指导 MathLLM 第三周的 FastAPI + Gradio 应用开发。目标是把训练好的数学模型包装成一个可操作、可解释、可评测的数学学习助手。

## 1. 产品定位

MathLLM 不应只是返回一个数字的计算器，而应能够理解题意、组织解题步骤、展示数学公式，并支持用户继续追问。

核心闭环：

~~~text
用户输入题目
      ↓
识别题型和已知条件
      ↓
规划解题方法
      ↓
逐步推导
      ↓
检查计算、条件和答案
      ↓
展示过程与最终答案
      ↓
支持用户继续追问
~~~

第一版的目标是稳定完成单题解答和多轮追问，不把 RAG、用户系统、在线题库和多模型竞技场放进首个 MVP。

## 2. 用户和典型场景

### 2.1 目标用户

- 需要理解解题过程的大学生；
- 想检查推导过程的学习者；
- 验证模型数学能力的项目开发者；
- 需要演示 LoRA 微调效果的评审者。

### 2.2 典型场景

#### 单题求解

用户输入：

~~~text
求解方程 x^2 - 5x + 6 = 0。
~~~

助手应说明题型，展示因式分解或求根公式的步骤，并明确标出最终答案。

#### 方法追问

用户继续问：

~~~text
可以不用因式分解，改用求根公式吗？
~~~

助手需要保留上下文，改用新的方法回答。

#### 修改条件

用户继续问：

~~~text
如果常数项改成 4，结果会怎样？
~~~

助手应理解“结果”指上一道题中的方程，并重新计算。

#### 答案核对

用户输入自己的答案：

~~~text
我算出的答案是 x=2 和 x=4，对吗？
~~~

助手应指出具体错误位置，不能只回复“对”或“不对”。

## 3. 功能需求

### 3.1 第一版必须具备的功能

| 功能 | 说明 | 对应组件 |
|---|---|---|
| 单题输入 | 接收中文、英文、数字和 LaTeX 题目 | Gradio Textbox |
| 单题解答 | 返回思路、步骤和最终答案 | /api/solve |
| 流式输出 | 逐段显示模型回答 | FastAPI SSE + Chatbot |
| Markdown 渲染 | 支持标题、列表和引用 | Gradio Chatbot |

| 清空对话 | 删除当前页面的历史上下文 | Gradio Button |
| 健康检查 | 显示后端和模型服务状态 | /api/health |
| 错误提示 | 处理超时、空输入和服务异常 | FastAPI + 前端 |
| 防重复提交 | 请求期间避免重复点击 | 前端事件状态 |

### 3.2 建议第一版加入的功能

- 示例题目快捷按钮；
- 重新生成；
- 显示当前模型名称和服务状态；
- 输入长度提示；
- 复制回答；
- 导出当前对话为 Markdown；
- 在回答中区分“解题过程”和“最终答案”；
- 显示“模型答案需要人工复核”的提示。

### 3.3 后续扩展功能

等单题、多轮和评测稳定后，再考虑：

- 图片上传和 OCR；
- 题型、学科和难度识别；
- 分步骤提示模式；
- 用户答案批改；
- 错题本和历史记录；
- RAG 题库检索；
- 基座模型、微调模型、量化模型对比；
- 多用户登录和权限管理。

## 4. 数学回答要求

### 4.1 推荐回答结构

模型应尽量使用以下结构：

~~~markdown
## 思路
说明题目类型和准备使用的方法。

## 解题步骤
1. 写出已知条件。
2. 进行关键变形或计算。
3. 解释每一步的依据。

## 结果检查
检查定义域、单位、符号、边界条件或代回结果。

## 最终答案
用独立、清晰的一句话给出最终结果。
~~~

简单题不必机械输出全部标题，但过程、结论和必要条件必须清楚。

### 4.2 不同题型的最低要求

| 题型 | 需要展示的内容 |
|---|---|
| 基础代数 | 变形依据、运算过程、解集 |
| 方程/不等式 | 定义域、等价变形、边界和解集 |
| 函数与微积分 | 定义域、公式、临界点或积分常数 |
| 极限 | 使用的极限性质、等价无穷小或展开条件 |
| 线性代数 | 矩阵变换、秩、行列式或特征值计算 |
| 概率论 | 事件定义、概率公式、结果范围 |
| 几何题 | 已知量、几何关系、单位和条件 |
| 应用题 | 变量定义、单位、方程建立和合理性检查 |

### 4.3 可靠性要求

系统应尽量做到：

- 不跳过影响结论的关键步骤；
- 不把猜测写成确定结论；
- 不忽略定义域、单位和边界条件；
- 不让过程与最终答案互相矛盾；
- 无法确定时明确说明不确定性；
- 对复杂或超出能力的问题提醒用户复核。

模型不能保证每次计算都正确，因此界面需要同时传达“可解释过程”和“需要复核”。

## 5. 页面信息架构

第一版建议使用一个主页面：

~~~text
MathLLM 数学解题助手
├── 顶部：标题、模型名称、服务状态
├── 主区域：对话和解题过程
│   ├── 欢迎说明或示例题
│   ├── 用户题目
│   └── 模型回答（Markdown + LaTeX）
├── 输入区域：题目输入框、解题按钮、清空按钮
├── 快捷操作：示例题、重新生成、复制/导出
└── 底部：模型版本、接口状态和使用提示
~~~

## 6. 主界面设计

### 6.1 空状态

用户还没有提问时，不要只展示一个空白聊天框，应提供说明和示例：

~~~text
┌──────────────────────────────────────────────┐
│ MathLLM 数学解题助手          ● 服务正常     │
├──────────────────────────────────────────────┤
│                                              │
│       请输入一道数学题，我会展示解题过程      │
│                                              │
│  示例：[解方程] [求导] [矩阵计算] [概率题]     │
│                                              │
├──────────────────────────────────────────────┤
│ 输入数学问题……                               │
│                              [解题] [清空]    │
└──────────────────────────────────────────────┘
~~~

用户应一眼知道：输入什么、系统会返回什么、服务是否正常。

### 6.2 对话区域

对话区域必须区分用户消息和助手消息：

~~~text
用户
求解 x^2 - 5x + 6 = 0

MathLLM
思路
这是一个一元二次方程，可以先进行因式分解。

解题步骤
...

最终答案
x=2 或 x=3
~~~

推荐约定：

- 行内公式使用 $x^2-5x+6=0$；
- 独立公式使用 $$x=\\frac{-b\\pm\\sqrt{b^2-4ac}}{2a}$$。

### 6.3 输入区域

输入区域应具备：

- 多行输入框；
- 支持粘贴 LaTeX；
- 支持 Enter 或 Ctrl+Enter 提交；
- 空输入不发送请求；
- 显示长度限制或超长提示；
- 发送后暂时避免重复提交；
- 回答完成后保留固定、一致的输入行为。

### 6.4 回答操作

建议为完整回答提供：

- 重新生成；
- 复制文本；
- 继续追问；
- 标记为错误答案；
- 导出 Markdown。

第一版至少要实现清空对话，复制和重新生成可以作为低成本增强功能。

## 7. 页面状态和反馈

### 7.1 加载状态

提交后应立即显示：

~~~text
正在分析题目……
~~~

流式内容到达后逐步追加，不要只显示一个无法判断进度的转圈图标。

### 7.2 完成状态

回答结束后：

- 保留完整 Markdown 和公式；
- 恢复解题按钮；
- 保存完整历史；
- 允许继续追问；
- 不重复追加同一份回答。

### 7.3 错误状态

错误信息应面向用户，不能直接显示 Python 堆栈：

| 技术错误 | 用户提示 |
|---|---|
| FastAPI 未启动 | 后端服务未启动，请检查 API 服务 |
| vLLM 未启动 | 模型服务暂时不可用，请稍后重试 |
| 请求超时 | 模型响应时间较长，请缩短题目或稍后重试 |
| 空响应 | 模型没有返回有效答案，请重新生成 |
| 输入为空 | 请输入数学题目后再提交 |
| 输入过长 | 题目或对话历史过长，请清空部分历史 |
| 服务端 500 | 模型服务发生错误，请查看服务日志 |

错误状态应允许用户重试，并尽量保留题目输入。

## 8. 前后端通信设计

### 8.1 服务拓扑

~~~text
浏览器
  ↓
Gradio 前端（本地 7860）
  ↓ HTTP/SSE
FastAPI（本地 8080）
  ↓ OpenAI 兼容 API
vLLM（云服务器或本地 8000）
  ↓
训练后的数学模型
~~~

本地开发不需要下载 7B 基座模型，也不需要本地 GPU。云服务器训练时，不建议同一块 GPU 同时运行训练和 FP16 vLLM；前端本地开发不受影响。

### 8.2 /api/health

健康检查必须实际请求 vLLM 的 /v1/models，不能固定返回成功。

成功响应示例：

~~~json
{
  "status": "ok",
  "vllm": "connected",
  "model": "mathllm-round5"
}
~~~

失败响应示例：

~~~json
{
  "status": "error",
  "vllm": "unavailable",
  "detail": "无法连接模型服务"
}
~~~

### 8.3 /api/solve

请求：

~~~json
{
  "question": "求解 x^2-5x+6=0",
  "stream": true
}
~~~

非流式响应建议统一为：

~~~json
{
  "content": "解题过程……",
  "finished": true,
  "model": "mathllm-round5"
}
~~~

### 8.4 /api/chat

请求：

~~~json
{
  "messages": [
    {"role": "user", "content": "求解 x^2-5x+6=0"},
    {"role": "assistant", "content": "解得 x=2 或 x=3。"},
    {"role": "user", "content": "换一种方法解。"}
  ],
  "stream": true
}
~~~

后端规则：

- system prompt 只添加一次；
- 只接受 user 和 assistant 历史角色；
- 最后一条消息必须是 user；
- 拒绝空消息和未知角色；
- 限制历史长度，避免超出上下文窗口；
- 前端不直接拼接模型特殊 token。

### 8.5 SSE 格式

~~~text
data: {"content":"首先，","finished":false}

data: {"content":"我们分析题目。","finished":false}

data: {"content":"","finished":true}
~~~

前端每收到一个 content 就更新回答区域，收到 finished=true 后保存完整历史。

## 9. 本地开发方式

### 9.1 推荐并行方式

~~~text
云服务器：训练模型或运行 vLLM
本地电脑：开发 Gradio + FastAPI + 页面交互
~~~

本地可以使用三种测试方式：

1. Mock 模式：后端返回固定答案，先验证界面和流式更新；
2. 本地 FastAPI + 云端 vLLM：通过 SSH 端口转发访问云端模型；
3. 云端完整部署：训练结束后，在云端运行 vLLM、FastAPI 和 Gradio。

### 9.2 本地启动

~~~powershell
cd D:\MathLLM
.\\.venv\\Scripts\\Activate.ps1
python -m app.api.main
~~~

另开终端：

~~~powershell
cd D:\MathLLM
.\\.venv\\Scripts\\Activate.ps1
python app/frontend/gradio_app.py
~~~

浏览器访问 http://localhost:7860。

当前 Gradio 前端默认调用 http://localhost:8080/api，也可以通过环境变量切换：

~~~powershell
$env:MATHLLM_API_URL = "http://localhost:8080/api"
python app/frontend/gradio_app.py
~~~

## 11. 测试与质量标准

### 11.1 功能测试

至少覆盖：

- 简单代数题；
- 一元二次方程；
- 极限、导数或积分题；
- 矩阵计算题；
- 概率题；
- 多行 LaTeX 题；
- 多轮追问；
- 修改上一题条件；
- 清空后新建对话。

### 11.2 异常测试

- vLLM 停止；
- FastAPI 停止；
- 地址配置错误；
- 输入为空或过长；
- 快速重复点击；
- 浏览器中途关闭；
- vLLM 返回 500；
- SSE 出现空 delta；
- 模型返回空内容。

### 11.3 测试记录

每道题建议记录：

~~~text
编号、题目、学科/题型、最终答案是否正确、
步骤是否完整、公式是否正常渲染、是否流式完成、
总耗时、是否报错、Bad Case 分类
~~~

模型准确率、API 稳定性和界面体验要分开记录，不能因为页面能显示就认为模型数学能力合格。

## 12. Bad Case 分类

### 模型问题

- 最终数值错误；
- 推导步骤错误；
- 漏掉定义域或边界条件；
- 过程和答案矛盾；
- 题意理解错误。

### 后端问题

- system prompt 重复添加；
- 历史顺序错误；
- vLLM 地址或模型名错误；
- SSE 解析错误；
- 超时没有捕获；
- 把异常堆栈返回给用户。

### 前端问题

- 流式文本没有逐步显示；
- LaTeX 显示为原始字符串；
- 清空后仍保留旧历史；
- 重复点击造成多条回答；
- 网络错误后按钮无法恢复；
- 移动端文本溢出。

## 13. 安全、隐私和边界

第一版至少应遵守：

- 不在前端暴露 SSH 密码、API Key 或模型凭据；
- 不把用户题目永久写入日志，除非明确用于评测；
- 日志中避免记录敏感输入；
- 限制输入长度和请求频率；
- 不宣传模型答案为绝对正确；
- 高风险场景提示人工复核；
- 生产环境不要使用 allow_origins=["*"]，应限制可信来源。

## 15. 模块化架构要求

这是本项目的硬性要求：**不同职责必须拆分到不同模块，不能把所有功能持续堆进一个文件**。新增功能前先确定它属于哪一层，再放到对应目录；不为了短期能运行而牺牲后续可维护性。

### 15.1 前端模块边界

~~~text
app/frontend/
├── gradio_app.py       页面布局、组件创建、事件绑定
├── controller.py       页面事件处理和状态更新
├── api_client.py       HTTP 请求、SSE 解析和后端错误转换
├── conversation.py     Gradio 历史与 API messages 的转换
└── config.py           前端地址、超时等运行配置
~~~

约束：

- 页面布局不直接实现 HTTP 请求；
- SSE 解析不写在 Gradio 组件文件中；
- 对话历史转换不散落在多个按钮回调里；
- 地址和超时使用配置模块或环境变量，不在业务函数中硬编码；
- 新增复制、导出、重新生成等功能时，应新增对应 service/helper，而不是继续扩大页面文件。

### 15.2 后端模块边界

后端实现时采用同样的分层方式：

~~~text
app/api/
├── main.py             创建 FastAPI 应用和注册路由
├── models.py           请求、响应和消息数据模型
├── routes/
│   ├── health.py       /api/health
│   ├── solve.py        /api/solve
│   └── chat.py         /api/chat
└── dependencies.py     配置、客户端和公共依赖

app/services/
├── vllm_client.py      调用 vLLM OpenAI 兼容 API
├── chat_service.py     system prompt、历史校验和上下文限制
└── stream_service.py   vLLM 流式响应到统一 SSE 的转换
~~~

后端路由只负责参数校验和返回响应，不能把 vLLM 调用、prompt 拼接、SSE 解析全部写在 main.py 中。

### 15.3 何时允许新增文件

满足以下任一条件时，应优先拆分模块：

1. 一个文件同时包含页面、网络请求和业务规则；
2. 一个函数承担输入校验、模型调用、结果格式化和错误处理四种职责；
3. 同一段逻辑需要在两个接口或两个页面复用；
4. 文件超过约 200–300 行且继续增长；
5. 单元测试无法只针对一个职责运行。

### 15.4 开发顺序

以后新增功能遵循：

~~~text
先定义模块职责
      ↓
再定义函数和数据结构
      ↓
实现独立模块
      ↓
由 main.py 或页面文件组装
      ↓
做模块级测试和端到端测试
~~~

这样可以避免先把所有逻辑写在一个文件，完成后再大规模重构。

## 17. 结论

当前项目最适合做成一个“单页面数学对话工作台”：

~~~text
顶部：MathLLM 标题 + 当前模型/服务状态
中部：大面积对话区，展示题目、步骤和最终答案
底部：多行题目输入框 + 解题 + 清空
辅助：示例题、错误提示、复制和重新生成
~~~

第一版不需要复杂导航、登录、题库和管理后台。先把“输入一道题 → 流式得到可读解答 → 继续追问 → 清空重来”做稳定，再根据 20–30 道手动测试和 Bad Case 迭代界面与模型。

## 18. 面向普通学生的功能补充与界面优化

前面的基础功能还不够构成一个好用的学习工具。面向普通学生时，系统还应帮助用户“学会怎么问、看懂过程、继续练习”，而不是只展示模型接口。

### 18.1 学生真正需要的功能

| 功能 | 学生能得到什么 | 当前优先级 |
|---|---|---|
| 示例题入口 | 不知道怎么开始时可以直接点题 | 已加入界面 |
| 简单解释追问 | 让模型换一种更容易理解的说法 | 第一版支持多轮 |
| 只给提示 | 避免一开始就看到完整答案 | 第一版通过追问支持 |
| 换一种方法 | 对比因式分解、公式法、几何法等思路 | 第一版通过追问支持 |
| 答案核对 | 粘贴自己的答案，让助手指出错误 | 第一版通过多轮支持 |
| 复制答案 | 方便整理笔记 | 界面提供复制入口 |
| 清空对话 | 开始下一道题，避免历史干扰 | 已实现 |
| 服务状态 | 知道当前是否可以提问 | 已加入顶部状态区 |
| 学习提示 | 让用户知道怎样提问效果更好 | 已加入侧栏 |
| 错误反馈 | 模型答错时可以记录问题 | 后续接入评测记录 |

这些功能不需要把页面做成复杂的后台系统。对于普通学生，清楚的引导和自然语言追问比大量按钮更重要。

### 18.2 学生版界面原则

- 少使用“checkpoint、量化、推理参数”等开发者术语；
- 首屏只突出“输入题目”和“开始解题”；
- 使用柔和背景、明确层级和较大的输入区域；
- 将示例题放在容易发现的位置；
- 对网络错误使用人话提示；
- 公式、步骤和最终答案保持足够间距；
- 移动端窄屏时自动变为单列布局；
- 不用复杂图表和过多设置打断解题过程。

### 18.3 当前界面布局

~~~text
┌──────────────────────────────────────────────┐
│ MathLLM 数学学习助手            服务状态      │
│ 把不会的题讲明白，把步骤一步一步说清楚        │
├───────────────────────────────┬──────────────┤
│                               │ 你可以这样问  │
│        对话与解题过程          │              │
│                               │ [示例题目]   │
│        Markdown / LaTeX       │ 学习小贴士   │
│                               │ 当前版本说明 │
│ ┌───────────────────────────┐ │              │
│ │ 输入数学问题……             │ │              │
│ └───────────────────────────┘ │              │
│       [开始解题] [清空对话]    │              │
└───────────────────────────────┴──────────────┘
~~~

顶部负责建立信任，中间负责阅读回答，右侧负责降低使用门槛，底部负责持续追问。

### 18.4 后续可加入的学生功能

在核心链路稳定后，可以增加：

1. **提示模式**：只给下一步提示，不直接给完整答案；
2. **难度选择**：基础解释、正常解释、竞赛级解释；
3. **错题收藏**：把当前题目和答案保存到本地；
4. **步骤折叠**：长答案按步骤展开，减少页面拥挤；
5. **练习同类题**：根据当前题目生成一道相似练习题；
6. **答案评价**：让用户标记“有帮助”或“答案有问题”；
7. **图片题目**：后续再加入 OCR，不在当前版本提前复杂化。

功能开发顺序应保持：

~~~text
稳定解题 → 清晰展示 → 追问与提示 → 错题和反馈 → 图片/OCR
~~~

### 18.5 外部大模型 API 接入

本地开发阶段可以先不下载或加载本地基座模型，使用以下链路：

~~~text
Gradio 前端
    ↓ localhost:8080
FastAPI 后端
    ↓ Authorization: Bearer API_KEY
外部 OpenAI 兼容模型 API
~~~

API 地址、模型名称和 API Key 由环境变量提供：

- `MATHLLM_API_BASE_URL`：例如 `https://api.example.com/v1`；
- `MATHLLM_MODEL_NAME`：服务商提供的模型名；
- `MATHLLM_API_KEY`：只在本地后端进程中使用。

前端不直接接触 API Key。Windows 用户可以双击项目根目录的 `start_local.bat`，启动器会打开 FastAPI 和 Gradio 两个窗口；也可以复制 `.env.local.example` 为 `.env.local` 后填写配置。

当前接入标准是 OpenAI 兼容的 `GET /models` 和 `POST /chat/completions`。如果某个服务商使用完全不同的请求格式，应新增独立 provider adapter，不要把分支逻辑塞进页面或 `main.py`。
