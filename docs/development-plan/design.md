# MathLLM 项目设计文档

## 一、项目背景与目标

### 1.1 要解决的问题

通用大模型（GPT-4、Qwen2.5-72B）在数学解题上表现良好，但存在以下问题：
- **成本高**：每次调用大模型 API 的 Token 消耗大，不适合高频使用
- **不可控**：无法针对特定数学领域（高数/线代/概率论）做定向优化
- **延迟高**：大参数量模型推理慢，用户体验差

小模型（7B）精调后可以在特定领域达到接近大模型的效果，同时具备：
- 推理速度快 5-10x
- 部署成本低（单卡即可运行）
- 可针对领域深度优化

### 1.2 项目目标

构建一个**端到端的数学解题大模型系统**，覆盖从数据准备到线上服务的完整链路：

```
数据收集 → 精调训练 → 模型量化 → 推理部署 → 应用开发 → 质量评测
```

### 1.3 目标指标（写进简历的数据）

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 领域准确率 | ≥ 85% | 在数学解题评测集上的正确率 |
| 相对基座提升 | ≥ 25 个百分点 | 精调模型 vs 未精调基座模型的提升幅度 |
| 首 Token 延迟 | ≤ 200ms | vLLM 部署后的首字响应时间 |
| 吞吐量 | ≥ 50 tokens/s | INT4 量化后的单卡推理速度 |
| 显存占用 | ≤ 6GB | INT4 量化后模型加载显存 |
| 对比 GPT-4 差距 | ≤ 10 个百分点 | 7B 精调模型 vs GPT-4 的准确率差距 |

## 三、数据规范

### 3.1 原始数据格式

支持以下格式的数据文件放入 `data/raw/`：

**JSONL 格式（推荐）：** 每行一个 JSON 对象
```jsonl
{"question": "求函数 f(x) = x^3 - 3x + 1 的极值点", "solution": "对 f(x) 求导...", "answer": "x=1 为极小值点, x=-1 为极大值点"}
{"question": "计算定积分 ∫(0 to π) sin(x)dx", "solution": "∫sin(x)dx = -cos(x) + C...", "answer": "2"}
```

**CSV 格式：**
```csv
question,solution,answer
"求矩阵 A=[[1,2],[3,4]] 的特征值","特征方程 det(A-λI)=0...","λ1=(5+√33)/2, λ2=(5-√33)/2"
```

### 3.2 训练数据格式（ChatML）

`prepare_data.py` 将原始数据转换为以下格式，存储在 `data/processed/`：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是一个专业的数学解题助手。请按照以下要求回答数学问题：\n1. 先分析题目要求\n2. 给出详细的解题步骤\n3. 用 LaTeX 格式书写数学公式\n4. 最后给出明确的答案\n5. 写出最终答案前，重新检查关键计算，并确认最终答案与解题过程一致\n6. 遇到进制问题，先确认数字的位数，再按位权展开；n 位 b 进制数按从高位到低位使用 b^(n-1), ..., b^1, b^0，不能混淆位数"
    },
    {
      "role": "user",
      "content": "求函数 f(x) = x³ - 3x + 1 的极值点"
    },
    {
      "role": "assistant",
      "content": "**分析题目要求**\n\n需要求函数 $f(x) = x^3 - 3x + 1$ 的极值点。\n\n**求解过程**\n\n第一步：对 $f(x)$ 求导：\n$$f'(x) = 3x^2 - 3$$\n\n第二步：令 $f'(x) = 0$：\n$$3x^2 - 3 = 0$$\n$$x^2 = 1$$\n$$x = \\pm 1$$\n\n第三步：二阶导数检验：\n$$f''(x) = 6x$$\n- $f''(1) = 6 > 0$，故 $x = 1$ 为极小值点\n- $f''(-1) = -6 < 0$，故 $x = -1$ 为极大值点\n\n**最终答案**\n\n极小值点 $x = 1$，$f(1) = -1$；极大值点 $x = -1$，$f(-1) = 3$。"
    }
  ]
}
```

### 3.3 数据来源建议

| 来源 | 数据量 | 获取方式 |
|------|--------|---------|
| GSM8K | 8,500 条 | HuggingFace 直接下载 |
| MATH (Hendrycks) | 12,500 条 | HuggingFace 直接下载 |
| 考研数学真题 | 500-1000 条 | 公开题库整理 |
| 大学高数/线代/概率论习题 | 1000+ 条 | 教材习题 + 自行构造 |
| 用 GPT-4 生成带解题过程的题目 | 500+ 条 | API 调用生成 |

建议训练集 **500-2000 条**即可看到明显效果（LoRA 数据效率很高）。

### 3.4 数据质量要求

- **question 不为空**，且长度 ≥ 5 字符
- **solution 包含完整步骤**，不只是答案
- **answer 可验证**（数值答案优先）
- **去重**：相似度 > 0.95 的样本去重
- **LaTeX 格式正确**：公式用 `$...$` 或 `$$...$$` 包裹

## 四、模型精调方案

### 4.1 为什么选 LoRA

| 方法 | 可训练参数 | 显存需求 | 训练速度 | 适用场景 |
|------|-----------|---------|---------|---------|
| Full Fine-tuning | 全部 (7B) | 80GB+ | 慢 | 有充足算力 |
| **LoRA** | **~0.1% (~7M)** | **16GB** | **快** | **本项目选择** |
| QLoRA | ~0.1% | 8GB | 中 | 显存极度有限 |

### 4.2 LoRA 原理简述（面试必备）

LoRA（Low-Rank Adaptation）的核心思想：不直接修改预训练权重 $W$，而是在旁边加一个低秩分解的增量：

$$W' = W + \Delta W = W + BA$$

其中 $B \in \mathbb{R}^{d \times r}$，$A \in \mathbb{R}^{r \times k}$，$r \ll \min(d, k)$。

- **r（rank）**：控制增量矩阵的秩，rank 越大表达能力越强但参数越多。经验值 8-32。
- **lora_alpha**：缩放因子，实际缩放比例 = alpha / r。通常设为 2r。
- **target_modules**：在 Transformer 的哪些线性层上添加 LoRA。通常加在 Attention 的 q/k/v/o 投影和 FFN 的 up/gate/down 投影上。

### 4.3 训练超参数选择依据

| 参数 | 配置值 | 选择理由 |
|------|--------|---------|
| learning_rate | 2e-4 | LoRA 微调常用范围 1e-4 ~ 5e-4，2e-4 是安全起点 |
| num_epochs | 3 | 数据量 500-2000 时，3 epoch 通常足够，过多会过拟合 |
| batch_size | 2 | 受显存限制，配合 gradient_accumulation 等效扩大 batch |
| gradient_accumulation | 8 | 等效 batch_size = 2×8 = 16，训练更稳定 |
| warmup_ratio | 0.03 | 短 warmup 适合小数据集微调 |
| max_seq_length | 2048 | 数学解题过程较长，需要足够的上下文窗口 |
| bf16 | true | 混合精度训练，减少显存占用同时保持数值稳定性 |

## 五、部署方案

### 5.1 vLLM 推理优化原理（面试必备）

vLLM 相比 HuggingFace 原生推理的核心优势：

- **PagedAttention**：借鉴操作系统的虚拟内存分页机制，将 KV Cache 分成固定大小的块，按需分配，避免显存碎片化。在批处理场景下显存利用率提升 2-4x。
- **Continuous Batching**：不等一个 batch 全部生成完才开始下一个，而是每个 token 生成完后立即插入新请求。吞吐量提升 5-10x。
- **CUDA Graph**：将多次 CUDA kernel 调用合并为一次提交，减少 CPU-GPU 通信开销。

### 5.2 量化方案对比

| 量化方式 | 显存占用 | 精度损失 | 速度 | 推荐场景 |
|---------|---------|---------|------|---------|
| FP16 | ~14GB | 无 | 基准 | 显存充足 |
| INT8 (bitsandbytes) | ~7GB | 极小 | 略慢 | 精度优先 |
| **INT4 (AWQ)** | **~4GB** | **小** | **快** | **本项目推荐** |
| INT4 (GPTQ) | ~4GB | 中等 | 快 | 备选 |

AWQ（Activation-aware Weight Quantization）根据激活值分布决定量化精度分配，对重要权重保留更高精度，数学场景比 GPTQ 精度更好。

### 5.3 API 接口文档

#### POST /api/solve

提交数学问题，返回解题过程。

请求：
```json
{
  "question": "求解方程 x^2 - 5x + 6 = 0",
  "stream": true
}
```

流式响应（SSE）：
```
data: {"content": "对", "finished": false}
data: {"content": "方程", "finished": false}
data: {"content": " $x^2 - 5x + 6 = 0$", "finished": false}
...
data: {"content": "因此 $x = 2$ 或 $x = 3$。", "finished": true}
```

#### POST /api/chat

多轮对话接口。

请求：
```json
{
  "messages": [
    {"role": "user", "content": "求解方程 x^2 - 5x + 6 = 0"},
    {"role": "assistant", "content": "...x=2 或 x=3..."},
    {"role": "user", "content": "如果改成 x^2 - 5x + 4 = 0 呢？"}
  ],
  "stream": true
}
```

#### GET /api/health

健康检查，返回模型加载状态和推理队列信息。

## 六、评测体系

### 6.1 评测维度

| 维度 | 方法 | 指标 |
|------|------|------|
| **答案准确率** | 提取最终答案，精确匹配/数值容差比较 | Accuracy (%) |
| **过程完整性** | LLM-as-Judge 打分（1-5 分） | Avg Process Score |
| **推理速度** | 记录首 Token 延迟和总生成时间 | First Token Latency (ms), Throughput (tokens/s) |
| **幻觉率** | 检测编造的公式/定理/计算错误 | Hallucination Rate (%) |
| **LaTeX 规范性** | 检查公式格式是否正确 | Format Score |

### 6.2 对比实验设计

| 实验组 | 说明 |
|--------|------|
| 基座模型（Qwen2.5-7B） | 不做任何精调，直接解题 |
| 精调模型（本项目） | LoRA 精调后的 7B 模型 |
| GPT-4 API | 作为上界参考 |
| 精调 + RAG（进阶） | 检索相关公式/定理作为上下文 |

### 6.3 消融实验

| 变量 | 取值 | 观测指标 |
|------|------|---------|
| LoRA Rank | 4, 8, 16, 32 | 准确率 + 训练时间 |
| 学习率 | 1e-4, 2e-4, 5e-4 | 准确率 + Loss 收敛曲线 |
| 训练数据量 | 100, 200, 500, 1000, 2000 | 准确率（数据效率曲线） |
| 训练 Epochs | 1, 2, 3, 5 | 准确率 + 过拟合检测 |

### 自我介绍中提及

> "我在实习期间发现大模型 API 调用成本高且不可控，因此独立完成了一个数学解题大模型项目——从数据准备到 LoRA 精调、量化部署、应用开发的全链路。精调后的 7B 模型在数学解题任务上准确率达到 XX%，接近 GPT-4 水平的 XX%，但推理成本降低了 95%。"

### 常见面试问题

**Q: LoRA 的 rank 怎么选？**
> rank 本质是在参数量和表达能力之间做 trade-off。我在消融实验中对比了 rank=4/8/16/32，发现 rank=16 在准确率提升开始趋于平缓，rank=32 略有提升但训练时间翻倍，综合考虑选择 rank=16。

**Q: 精调数据量多少合适？**
> LoRA 的数据效率很高。我的实验显示 500 条数据就能看到明显效果（准确率提升 XX 个百分点），到 1000 条后提升趋于平缓。最终使用 XX 条数据训练 3 个 epoch。

**Q: 为什么用 vLLM 而不是 HuggingFace 原生推理？**
> vLLM 的 PagedAttention 解决了 KV Cache 显存碎片化问题，Continuous Batching 让请求可以动态插入，在高并发场景下吞吐量比原生推理高 5-10 倍。

**Q: 怎么评测模型效果？**
> 我设计了多维度评测体系：答案准确率用精确匹配+数值容差，解题过程用 LLM-as-Judge 打分，同时追踪推理延迟和幻觉率。对比了精调模型、基座模型和 GPT-4 三个版本的表现。
