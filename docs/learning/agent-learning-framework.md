# Agent 学习框架

本文面向已经接触过大模型微调、RAG、FastAPI 和 vLLM 的学习者，按照由浅入深的顺序梳理 Agent 的核心知识、实践重点、常见问题和面试问题。

## 一 学习目标

Agent 不是一个单独的模型，而是由大模型、Prompt、工具、状态、记忆、工作流、验证机制和工程服务组成的应用系统。

最终建议围绕现有 MathLLM 和 RAG 项目，构建一个数学学习 Agent：

```text
用户提问
    ↓
任务分类与结构化路由
    ├── 数学题 → MathLLM
    ├── 数学知识 → RAG
    ├── 需要计算 → Python 计算工具
    └── 普通问题 → 通用大模型
             ↓
        答案验证与纠错
             ↓
          最终回答
```

## 二 总体学习路线

```text

        ↓
```

每个阶段都建议分成三层：

1. 入门：理解概念和整体调用链路。
2. 实践：能够独立完成一个小功能。
3. 深入：能够处理异常、成本、安全和性能问题。

## 三 Prompt 与结构化输出

### 需要掌握的知识

- System、User、Assistant 消息的作用。
- 角色、任务、输入、约束、输出格式和异常处理。
- Zero-shot、Few-shot 和示例驱动 Prompt。
- JSON 输出、枚举值、字段约束和 JSON Schema。
- Pydantic 等结构化数据校验工具。
- 模型输出格式错误时的重试和兜底。

### Agent 中的作用

Agent 经常需要让模型判断任务类型或选择下一步动作。例如：

```json
{
  "intent": "math",
  "tool": "math_solver",
  "query": "求解 x^2 - 5x + 6 = 0",
  "answer_style": "step_by_step"
}
```

结构化输出是大模型和程序逻辑之间的桥梁。没有稳定的结构化输出，程序就无法可靠地进行路由和工具调用。

### 实践任务

定义一个任务路由结构：

```python
from typing import Literal
from pydantic import BaseModel


class RouteDecision(BaseModel):
    intent: Literal["math", "knowledge", "general"]
    tool: Literal["math_solver", "rag", "none"]
    query: str
    answer_style: Literal["direct", "step_by_step", "hint"]
```

然后让模型判断问题应该交给 MathLLM、RAG 还是直接回答。

### 常见问题

- 模型输出 Markdown 代码块而不是 JSON。
- 模型生成不存在的字段。
- 字段值不符合程序定义的枚举。
- 用户输入覆盖系统规则。
- Prompt 太长，真正的约束反而不突出。
- 让模型输出过多解释，导致程序难以解析。

### 需要回答的面试问题

- 什么是结构化输出？
- 为什么 Agent 需要结构化输出？
- 如何保证模型输出符合 JSON Schema？
- 模型输出错误时如何处理？

## 四 Function Calling

### 核心流程

```text
用户问题
    ↓
模型判断需要使用工具
    ↓
输出工具名称和参数
    ↓
程序校验并真正执行工具
    ↓
工具结果返回给模型
    ↓
模型生成最终答案
```

模型不会直接执行函数。模型只负责提出调用请求，程序负责校验、授权和执行。

### 需要掌握的知识

- 工具名称和工具描述。
- 工具参数与 JSON Schema。
- 必填参数、默认参数和参数类型。
- 单工具和多工具调用。
- 并行工具调用。
- 工具结果如何重新输入模型。
- 工具调用失败后的处理。

### 适合当前项目的工具

```python
search_knowledge(query)
solve_math_problem(question)
calculate_expression(expression)
check_math_answer(question, answer)
```

### 常见问题

- 模型选择了错误的工具怎么办？
- 工具参数缺失怎么办？
- 工具返回内容太长怎么办？
- 工具是否可以执行任意代码？
- 多个工具是否应该并行执行？

## 五 ReAct Agent

### 基本思想

ReAct 将任务分为推理、行动和观察：

```text
分析任务 → 选择行动 → 获取观察结果 → 继续分析 → 输出答案
```

例如用户询问企业制度，Agent 可以判断需要调用知识库，然后根据检索结果回答；如果检索结果不足，可以改写查询或结束并说明无法回答。

### 需要掌握的知识

- Action 如何表示。
- Observation 如何返回。
- Agent 循环如何结束。
- 最大循环次数。
- 工具结果如何影响下一步。
- ReAct、Chain 和 Workflow 的区别。

### 常见问题

- Agent 无限循环。
- Agent 重复调用同一个工具。
- 工具返回空结果后仍然编造答案。
- Agent 不知道什么时候应该停止。
- 为了简单任务使用 Agent，导致响应变慢、成本变高。

### 基本判断

- Chain：步骤基本固定。
- Workflow：步骤由程序预先控制。
- Agent：步骤由模型根据任务动态决定。

## 六 工具封装与异常处理

### 工具接口应包含

- 工具名称。
- 功能说明。
- 输入参数。
- 输出结构。
- 超时时间。
- 异常类型。
- 权限限制。
- 日志字段。

RAG 工具建议返回结构化结果：

```json
{
  "success": true,
  "documents": [
    {
      "content": "检索到的文本",
      "source": "knowledge_base.txt"
    }
  ]
}
```

### 需要学习的工程机制

- 参数校验。
- 超时。
- 重试和指数退避。
- 降级和备用模型。
- 熔断。
- 幂等性。
- 日志和链路追踪。
- 权限控制。

### 常见异常

- API Key 错误。
- 网络请求超时。
- 模型服务不可用。
- 向量库读取失败。
- 检索不到相关内容。
- 返回结果超过上下文长度。
- 工具被重复调用。

关键原则：工具失败时，要把失败状态明确返回给 Agent，不能让 Agent 把错误信息当成正常答案。

## 七 RAG Agent

现有 RAG 项目属于基础 RAG：

```text
问题 → 文档切分 → 向量化 → 相似度检索 → 大模型回答
```

RAG Agent 则增加了决策能力：

```text
问题
 ↓
判断是否需要检索
 ↓
选择知识库
 ↓
改写查询
 ↓
执行检索
 ↓
判断结果是否充分
 ↓
回答或继续检索
```

### 需要掌握的知识

- 文档加载。
- 文本切分。
- Embedding。
- 向量数据库。
- 相似度检索。
- Top-k。
- 查询改写。
- 多轮检索。
- Reranker 重排序。
- 来源引用。
- 检索失败处理。
- 多知识库路由。

### 结合当前 RAG 项目学习

当前项目使用 LangChain、Chroma、DashScope Embedding、`text-embedding-v3` 和 `qwen-plus`，文本切分参数为 chunk size 500、overlap 50，检索数量为 3。

需要进一步理解：

- 为什么 chunk size 设置为 500？
- overlap 对检索有什么作用？
- Top-k 太大或太小有什么影响？
- 如何判断检索结果是否真的相关？
- 为什么检索到了相关内容，模型仍然回答错误？
- 如何加入来源引用？
- 如何处理知识库中没有答案的问题？

### 面试问题

- RAG 和微调有什么区别？
- RAG 为什么可以减少幻觉？
- 向量检索的原理是什么？
- 如何评估 RAG 的检索效果？
- 如何解决文档切分不合理？
- 什么情况下不应该使用 RAG？

## 八 记忆系统

### 记忆类型

#### 短期记忆

当前对话历史。

#### 工作记忆

当前任务的中间结果，例如已经检索到的文档、调用过的工具和当前解题步骤。

#### 长期记忆

跨多次对话保存的用户偏好、历史任务和重要信息。

#### 语义记忆

以向量形式保存的知识内容，RAG 知识库属于这一类。

### 需要掌握的知识

- 对话历史裁剪。
- 历史摘要。
- 向量记忆。
- 记忆写入和删除策略。
- 记忆冲突处理。
- 用户数据隔离。
- 隐私和敏感信息保护。

### 常见问题

- 对话太长，超过上下文怎么办？
- 什么信息应该保存为长期记忆？
- 错误信息进入长期记忆怎么办？
- 用户如何查看和删除自己的记忆？
- 多个用户的记忆如何隔离？

关键原则：不是所有对话内容都应该写入长期记忆。

## 九 LangGraph 工作流

LangGraph 适合构建有状态、有分支、有循环、可恢复的 Agent 工作流。

### 核心概念

- State：状态。
- Node：处理节点。
- Edge：节点之间的连接。
- Conditional Edge：条件路由。
- Checkpoint：状态检查点。
- Interrupt：中断。
- Human-in-the-loop：人工参与。

### 数学学习 Agent 示例

```text
问题分类节点
    ↓
条件路由
    ├── RAG 检索节点
    ├── MathLLM 求解节点
    └── 普通回答节点
           ↓
      答案验证节点
           ↓
      最终回答节点
```

### 需要掌握的知识

- 如何定义 State。
- 节点之间如何传递数据。
- 如何添加条件边。
- 如何实现循环和重试。
- 如何保存中间状态。
- 如何暂停等待人工确认。
- 如何从检查点恢复任务。

### 常见问题

- 状态中应该保存什么？
- 如何防止工作流进入死循环？
- 任务中断后如何恢复？
- LangGraph 和普通 Python 流程控制有什么区别？
- LangGraph 和 LangChain Agent 有什么区别？

## 十 Reflection 与结果验证

Reflection 的基本流程是：

```text
第一次生成结果 → 检查结果 → 发现问题 → 修改或重新生成
```

但不要只依靠模型自我评价，最好结合规则、计算工具或独立验证模型。

### MathLLM 中的验证

```text
模型解题
  ↓
提取最终答案
  ↓
Python 重新计算
  ↓
比较结果
  ↓
正确则返回，错误则重新生成
```

### RAG 中的验证

```text
生成回答
  ↓
检查回答能否在检索内容中找到依据
  ↓
检查是否出现知识库之外的结论
  ↓
补充引用或拒绝回答
```

### 需要掌握

- 格式验证。
- 数学计算验证。
- 来源一致性验证。
- LLM Judge。
- Critic Agent。
- 自动重试。
- 最大重试次数。

### 常见问题

- 模型自我反思会不会重复错误？
- 如何判断第一次回答真的错了？
- 验证器是否需要使用独立模型？
- 什么时候应该重新生成？
- 重试次数过多如何处理？

## 十一 Multi-Agent

### 常见角色

- Planner：任务规划。
- Researcher：资料搜索。
- Retriever：知识库检索。
- Solver：问题求解。
- Critic：结果检查。
- Summarizer：结果总结。

数学学习 Agent 可以拆分为：

```text
规划 Agent
    ↓
知识检索 Agent
    ↓
数学求解 Agent
    ↓
答案验证 Agent
    ↓
讲解生成 Agent
```

### 常见架构

- Manager：主 Agent 负责调度其他 Agent。
- Pipeline：多个 Agent 按顺序执行。
- Debate：多个 Agent 分别回答，再由评审 Agent 选择。
- Handoff：一个 Agent 将任务转交给另一个 Agent。

### 常见问题

- 为什么需要多个 Agent？
- 多 Agent 是否一定比单 Agent 好？
- Agent 之间如何共享状态？
- 如何避免多个 Agent 重复工作？
- 如何控制 Token 和 API 成本？

建议先完成单 Agent，再尝试“主 Agent + RAG 工具 + MathLLM 工具 + 答案验证器”。

## 十四 推荐实践路线

### 阶段一：基础 Agent

学习 Prompt、结构化输出、Function Calling 和简单单 Agent。

目标：模型能够根据问题选择一个工具。

### 阶段二：RAG Agent

学习查询改写、知识库路由、检索结果判断、来源引用和检索失败处理。

目标：让现有 RAG 项目能够自主判断是否检索，并对无答案情况进行处理。

### 阶段三：工作流 Agent

学习 LangGraph、状态管理、条件路由、循环、检查点和人工确认。

目标：把 RAG 和 MathLLM 连接成完整的数学学习工作流。

### 阶段四：生产级 Agent

学习 Reflection、Multi-Agent、评测、日志、安全、性能优化和部署。

目标：能够解释 Agent 系统为什么可靠、可控、可维护。
